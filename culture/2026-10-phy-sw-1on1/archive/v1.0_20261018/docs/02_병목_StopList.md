# 02. 개발 프로세스 병목 분석 & Stop-List — Workflow Optimizer

> 입력: `01_진단_결과.md`, 조직 배경 문서(과제 목록, GitHub 전환, 회의 피드백)
> 원칙: 더하기가 아니라 **버리기(Subtraction)**. 항목마다 "현재 비용 → 조치 → 기대 효과"로 씁니다.

## 결론 (먼저)

- 병목은 네 군데입니다. **① GitHub 전환 오버헤드, ② 레거시 칩셋 폴더, ③ 목적 없는 회의, ④ 과제 중복 할당**. 이 중 ②와 ③은 리더 결정만으로 1주 안에 제거할 수 있는 Quick-Win입니다.
- Stop-List 1차 후보는 **회의 3종, 과제 4건**입니다. 이를 공식 종료·보류 선언하는 것이 "흐지부지"에 대한 가장 강한 반대 신호입니다.
- 회의는 **3P(Purpose·Product·People)** 미기재 시 신설 금지, 진도 점검은 Jira 비동기 전환을 기준으로 삼습니다.

## 2. Stop-List (즉시 중단·보류 후보, 우선순위순)

| 순위 | 항목 | 유형 | 조치 | 중단 사유 | 영향 |
|---|---|---|---|---|---|
| 1 | 방향 미정 상태의 다인원 과제 회의 | 회의 | 폐지 → 3명 이하 결정 회의로 대체 | "다음 주에도 똑같은 소리"라는 체감. 결정 없는 회의는 비용만 발생 | 즉시 주당 수 시간 회수 |
| 2 | 이름만 다른 중복 진도 점검 회의 | 회의 | 통합 1개 + Jira 비동기 | 같은 내용을 여러 회의에서 반복 보고 | 참석자 피로 감소 |
| 3 | 참석 이유가 불명확한 전체 참석 회의 | 회의 | People 명시 후 필수 참석자만 | 3P 미충족 | SCI ① 회의 효율 직접 개선 |
| 4 | 종료 기준 없는 그룹 내 개선 activity | 과제 | 종료 기준·오너·마감 없는 항목 공식 보류 선언 | "흐지부지" 반복이 학습된 무력감의 원천 | 신뢰 회복 신호 |
| 5 | 상용 이슈 담당자의 선행 과제 겸임 | 과제 | 겸임 해제, 선행 과제는 선행 파트로 | 우선순위 충돌, 양쪽 모두 지연 | 상용 이슈 처리 집중 |
| 6 | 상용 계획·regression 없는 레거시 칩셋 폴더 | 과제(정리) | archive 후 메인 제거 | CL 제출 오버헤드 | PR 범위 축소 |
| 7 | 성과 미달 해외 연구소 과제 | 과제 | 범위 축소 또는 보류 | 일부 연구소만 성과. 관리 로드가 국내 과제를 잠식 | 리더 시간 회수 |
| 8 | 메인 과제에 반영되지 않는 개인 AI 사이드 과제 | 과제 | 메인 log analysis 과제에 흡수하거나 종료 | 노력이 반영 안 되어 사기 저하 | 노력의 의미 복원 |

## 3. 회의 3P 기준 & 비동기 커뮤니케이션

### 3P 기준 (신설·유지 조건)

| P | 질문 | 미충족 시 |
|---|---|---|
| Purpose | 이 회의로 무엇을 **결정**하는가? (정보 공유만이면 문서로) | 신설 금지 / 폐지 |
| Product | 회의가 끝나면 무엇이 **남는가**? (결정 사항, 담당, 마감) | 회의록 템플릿 강제 |
| People | 결정에 **꼭 필요한 사람**은 누구인가? (참고인은 회의록 공유) | 참석자 축소 |

### 비동기 상태 공유 모델

- 진도 점검: Jira 보드 상태 + 주 1회 3줄 코멘트(한 일 / 막힌 것 / 다음 주). 회의 없음.
- 결정 필요: 2명 이상 의견 충돌 시에만 30분 결정 회의 소집, 결정자 1명 지정.
- 전체 공유: 격주 그룹 미팅 1회로 통합. 마일스톤·과제 현황·Stop-List 변경을 한 장으로 공유(SCI ③ 목적·배경 설명 대응).

## 4. Git/GitHub 리팩토링 스펙

1. **브랜치 전략 1장 가이드**: feature 브랜치 → `git fetch` → `git rebase origin/main` → 충돌 해결 → `git push --force-with-lease`. "꼬이면 전부 삭제" 대신 `git reflog`로 복구하는 법을 함께 적는다.
2. **PR 템플릿 축소**: 목적(1줄) / 변경 범위(칩셋·모듈) / 테스트 결과(regression 링크) 3항목만 필수. 나머지는 선택.
3. **레거시 폴더 정리 절차**: 인벤토리 → TL 확인 → archive 브랜치 이동 → 메인 제거 → 공지. 되돌릴 수 없는 명령(강제 삭제)은 쓰지 않고 archive 브랜치로 보존.
4. **GitHub 페어링**: 시니어 1명 + 주니어 2명, 2주간 PR을 함께 올린다. 종료 시 주니어가 가이드 1장을 보강한다(주니어-시니어 접점 복원 효과 겸용).
5. **파일 history 추적**: `git log --follow`, GitHub blame 뷰 사용법을 가이드에 포함.
